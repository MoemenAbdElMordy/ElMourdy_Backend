# Rails Database Learning Guide

## What was built

This project started with a Rails API application and then added a production-oriented MySQL schema, database constraints, Active Record models, transactional services, deterministic seeds, automated tests, linting, and security scanning.

## Tools and packages

### Ruby and Rails

- Ruby runs the language and the command-line tools.
- Rails provides the API framework, Active Record ORM, migrations, validations, tests, and application structure.
- The project was created in API mode, so browser views and asset-pipeline features are not part of the main request cycle.

### mysql2

The `mysql2` gem is the Active Record adapter for MySQL. Rails uses it through `config/database.yml` and environment variables.

### bcrypt

The `bcrypt` gem powers `has_secure_password`. The raw password is never stored. BCrypt writes a slow password hash to `password_digest` and provides the `authenticate` method.

### rack-cors

The `rack-cors` gem adds CORS headers so the separately hosted frontend can call the API. The allowed frontend origin comes from `FRONTEND_ORIGIN`.

### Minitest

Rails includes Minitest. Tests live under `test/` and run inside database transactions by default, keeping tests isolated.

### RuboCop

RuboCop checks Ruby formatting and style. The project uses the Rails Omakase rules generated by Rails.

### Brakeman

Brakeman statically scans Rails code for common security problems such as unsafe SQL, dangerous redirects, and mass-assignment mistakes.

### Bundler Audit

Bundler Audit compares locked gem versions with known vulnerability advisories.

## Important files

### `Gemfile`

Declares direct Ruby dependencies. `bundle install` resolves these dependencies and writes exact versions to `Gemfile.lock`.

### `config/database.yml`

Defines development, test, and production database connections. Credentials come from environment variables, not committed files.

### `config/application.rb`

Enables Rails API mode, sets Cairo as the application time zone, and stores database timestamps in UTC.

### `config/initializers/cors.rb`

Configures the frontend origin and allowed HTTP methods.

### `db/migrate/20260718000100_create_el_mourdy_core_schema.rb`

Creates the original tables, columns, foreign keys, and indexes. It is the structural foundation of the database.

### `db/migrate/20260719000100_harden_core_schema.rb`

Adds database check constraints and explicit delete behavior without rewriting migration history. This is the correct approach after an earlier migration has been shared.

### `db/migrate/20260719000200_remove_redundant_indexes.rb`

Removes single-column indexes that MySQL created for foreign keys after a composite left-prefix index became available. Its explicit `down` method restores every removed index during rollback.

### `db/schema.rb`

Rails generates this file from the live database. It is a readable snapshot and can load a new database faster than replaying every historical migration.

### `app/models/`

Each model maps a Ruby class to a database table. Models define associations, enums, validations, and reusable query scopes.

### `app/models/concerns/`

Concerns hold reusable model behavior. `E164Phone` centralizes phone validation, while `Publishable` centralizes content status and visibility queries.

### `app/services/`

Service objects implement multi-record business operations. They keep transactions and locking logic out of controllers and make the workflows independently testable.

### `db/seeds.rb`

Creates idempotent baseline data. Running the seed task repeatedly does not create duplicate grades, academic years, or the initial teacher.

### `test/`

Contains model, service, database-integrity, and repository-policy tests. The integrity tests deliberately bypass Active Record validations to prove that MySQL itself rejects invalid rows.

### `.github/workflows/ci.yml`

Starts MySQL in GitHub Actions and runs tests, RuboCop, Brakeman, and Bundler Audit for every pull request and every push to `main`.

## Commands used

### Create the API application

```bash
rails new ElMourdy_Backend --api --database=mysql --skip-git --skip-bundle
```

- `--api` removes browser-oriented middleware and generated views.
- `--database=mysql` selects the mysql2 adapter.
- `--skip-git` lets repository creation happen after generated files are reviewed.
- `--skip-bundle` delays dependency installation until the Gemfile is reviewed.

### Install dependencies

```bash
bundle install
```

### Create and migrate databases

```bash
bin/rails db:prepare
bin/rails db:migrate
bin/rails db:migrate:status
```

- `db:prepare` creates the database when necessary and loads or migrates the schema.
- `db:migrate` runs pending migration classes in timestamp order.
- `db:migrate:status` shows which migrations are applied.

### Prepare and seed data

```bash
bin/rails db:seed
```

### Run tests

```bash
bin/rails db:test:prepare
bin/rails test
```

### Run quality and security checks

```bash
bundle exec rubocop
bundle exec brakeman --no-pager
bundle exec bundler-audit check --update
```

### Inspect the Rails application

```bash
bin/rails runner "Rails.application.eager_load!; puts ApplicationRecord.descendants.map(&:name).sort"
```

`rails runner` executes Ruby code with the full Rails environment loaded. It is useful for diagnostics and controlled maintenance tasks.

## How a migration works

A migration is a Ruby class with a versioned filename. Rails records applied versions in `schema_migrations`. The `change` method uses a Ruby DSL that Active Record translates into MySQL DDL statements.

For example:

```ruby
add_check_constraint :grades, "level BETWEEN 1 AND 3", name: "chk_grade_level"
```

This creates a named MySQL constraint. Naming constraints makes production errors and future migrations easier to understand.

## How an association works

```ruby
belongs_to :academic_year
has_many :branches, dependent: :restrict_with_error
```

`belongs_to` expects an `academic_year_id` foreign key. `has_many` provides collection queries. `restrict_with_error` prevents an application-level delete when historical child rows exist; the database foreign key remains the final safeguard.

## How an enum works

```ruby
enum :status, { draft: 0, published: 1, hidden: 2, archived: 3 }, validate: true
```

MySQL stores a compact integer. Ruby code uses readable methods such as `published?`, `published!`, and `Exam.published`.

## Why transactions and locks matter

A transaction makes a group of writes succeed or fail together. A row lock prevents another transaction from changing the same protected row until the current transaction finishes.

Without locking, two requests could read one unused code and both attempt to redeem it. The service locks the code row before checking state. The unique indexes and foreign keys remain a second line of defense.
